# Chat queue and user decisions

Chat 1.14.0 provides a per-conversation queue above the composer. While a response runs, Enter or Queue adds the current draft and leaves Stop separate. Each queued item captures its model/provider configuration, notes, attachments, selected skills, project instructions and tools. Items execute in order after successful responses and see preceding conversation context. Edit, Move up, Move down and Remove are available through visible and right-click menus. Editing pauses the queue until Resume.

Stop, denial, error, history changes and app restart pause queued work. Opening another chat does not interrupt a run. A restart never automatically sends saved queued messages. Branching a chat copies history without copying its pending queue. A changed provider configuration leaves the queued item intact with an error. Queue admission and draft removal are atomic; dequeue and history insertion are atomic, so failed preflight/save does not drop or duplicate a message. Queues share the existing three-run limit and allow twenty items per chat.

Tool-capable models receive `request_user_input`. A question appears inline with suggested answers and free text; Send answer resumes the same tool request. Composer messages still go to the queue and cannot accidentally answer the question. Answered questions remain part of subsequent context even when the provider fails afterward. Stopping or restarting cancels a pending question; an old decision cannot resume an interrupted run.

The + menu has Ask before tool actions. Off is the default: explicitly selected provider tools and bounded document creation/revision run without repetitive confirmations. Turning it on requests host-enforced approval for document writes and selected hosted capabilities. Reads need no extra approval. Allow once covers the pending action. Allow for this chat covers that named tool while the app remains open; changing approval mode or restarting clears the grant. Hosted approval covers use of that capability for the current provider request, because hosted sub-actions execute inside the provider. Deny ends the run and pauses the queue, preventing the provider from using another method to perform the denied action.

Approval/clarification cards are persisted, but suspended provider continuations are not replayed after restart. Human waiting time is excluded from provider execution deadlines; network and ordinary tool execution timeouts remain enforced. Cancellation remains immediate. Models without function support remain ordinary chat and do not gain a false structured-question capability.

Sonnet 5 and Opus 5 are included in the documented Anthropic client-tool allowlist. End-to-end isolated tests use the actual Anthropic adapter and local document renderer to verify a real DOCX, its response card, tool-result continuation and durable artifact without requiring hosted code execution or an installed skill. Installed skills remain explicitly selected instructions; tool events do not imply a skill was loaded.

Tests exercised actual DOCX ZIP content through mocked Anthropic SSE, durable artifact restart, queue snapshots and atomic dispatch, cancellation/denial, retained clarification answers, and human-wait deadlines across providers.
